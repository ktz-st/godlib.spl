# demOS starfield / GodLib

`STARS.PRG`: three-plane 3D starfield for Atari ST/STE, 320x200, 1 MB RAM.
Port of J.Hubert's `demOS/FX/STARFILD/STARFILD.C` and `STARFILD.S` (MIT;
see `LICENSE.demOS`). The star area is 320x152 at y=24; the remaining rows
hold an independent static title and instructions.

```sh
make -C /Users/kriss/GCC.ELF/godlib.spl/starfield
```

- `1`, `2`, `3`, `4`: 96, 192 (default), 384, 768 stars.
- Space: pause/resume, including screen flips.
- Esc: restore the desktop.

## Renderer

The original demOS approach is retained: 128 precomputed projection depths per
trajectory, and generated pixel routines for every screen X and six brightness
colours. C prepares the tables and machine code once at startup; the animation
and erasing run in 68000 ASM, without per-frame division or a full-screen copy.
Initialisation takes a few seconds on an ST 8 MHz.

The generated routines use OR/BSET, save the touched group-byte address, and
DBRA straight back into the star loop. All 32,448 generated bytes fit within
the signed 16-bit branches; generation checks the branch range. Depth 127 and
out-of-bounds X positions reset a star using cyclic random trajectory tables.
Different star colours can combine when their pixels overlap.

Each GodLib screen page has its own erase list and previous star count. All old
stars on a page are erased before any new ones are drawn. This works on a black
background: it clears complete bytes in the three star planes, not arbitrary
background graphics. The fourth plane is preserved. Decreasing the star count
still erases all stars previously drawn on each page.

Port changes include GCC's full 32-bit callee-saved registers, 320-pixel width,
absolute trajectory pointers with zero sentinels, and saving the group base
rather than the first nonzero colour plane. The erase kernel clears three
planes with MOVEP.W plus MOVE.B instead of clearing four planes with MOVEP.L.
No blitter, STE scrolling registers, or timer interrupts are needed.

## Verification and profiling

```sh
make -C /Users/kriss/GCC.ELF/godlib.spl/starfield debug
python3 /Users/kriss/GCC.ELF/godlib.spl/starfield/analysis/verify-hatari.py
python3 /Users/kriss/GCC.ELF/godlib.spl/starfield/analysis/profile.py
```

The scripts use the installed `hatari-debugging` skill helpers and local TOS
ROMs. Functional checks independently project the star positions and compare
all 24,320 bytes of the star field, including erased areas and the untouched
fourth plane. They also check count changes, pause/resume and clean exit.

The profiler starts a fresh Hatari-hrdb process for each count. Measurements
include the main ASM draw loop, generated pixel code, resets and erase routine.
They exclude startup table generation, C/input/frame bookkeeping, VBL handlers
and waiting for the next frame. Percentages are the kernel's share of a
160,256-cycle PAL frame, not the emulator's host CPU usage. Target frame/VBL
counters separately measure the actual update rate.

### Measured cost: ST 8 MHz, 1 MB, TOS 2.06

| Stars | Draw cycles | Erase cycles | Total time | PAL frame budget | Updates/s |
|---:|---:|---:|---:|---:|---:|
| 96 | 15674 | 4006 | 2.46 ms | 12.3% | ~50 |
| 192 | 30879 | 7852 | 4.84 ms | 24.2% | ~50 |
| 384 | 61307 | 15543 | 9.61 ms | 48.0% | ~50 |
| 768 | 122195 | 30922 | 19.14 ms | 95.5% | ~50 |

Default 192 stars uses about 24.2% of the frame for the renderer. At 768 stars
there is very little time left for additional application work, although this
standalone example maintained approximately 50 updates/s in the capture.
Counters measured 304–305 updates per 305 VBLs; the one-update difference is
within the sampling boundary. Values are emulator measurements, not a physical
ST benchmark. Raw totals and counter deltas are in `analysis/profile.json`.

Functional verification passed on ST / TOS 2.06 and STE / TOS 1.62, both with
1 MB RAM and a 68000 at 8 MHz: eight independently reconstructed frames per
configuration, both screen pages observed, all four star counts, count reduction,
pause/resume and return to TOS. See `analysis/results-*.json`.
